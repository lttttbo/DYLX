Android Guest 至外部 PC 的 UDP 上行带宽异常调查报告
1. 调查背景与目标
当前产品以修改版 Xvisor 为虚拟化基础，ServerVM 运行 Linux 和 DSM，Android 作为用户虚拟机。Android 的虚拟网卡由 DSM 提供，数据经 tap1 接入 ServerVM 的 br0，再由物理网卡 eth0 与外部 PC 通信。
网络拓扑如下：
Android Guest
      │
      │ virtio-net
      ▼
DSM / vhost-net
      │
      ▼
    tap1
      │
      ▼
     br0
      │
      ▼
ServerVM eth0
      │
      ▼
   外部 PC
最初发现的问题是：Android 向外部 PC 发送 1400 字节 UDP 报文时，上行带宽长期只能达到约 500～650 Mbps；但其余场景基本正常：
场景	测试结果
Android → PC，UDP 上行	异常，约 500～650 Mbps
PC → Android，UDP 下行	正常，约 930 Mbps 以上
Android ↔ PC，TCP	正常，约 930 Mbps 以上
Android → ServerVM，UDP	正常，明显高于 1 Gbps
ServerVM → PC，UDP	正常，约 950 Mbps
ServerVM ↔ PC，TCP	正常
因此，本次调查的核心问题不是简单确认“网络慢”，而是解释：
	1.	为什么只有 Android→PC 的 UDP 上行受影响；
	2.	问题位于 Android、virtio-net、DSM/vhost、bridge，还是物理网卡；
	3.	为什么关闭 vhost 后最初也没有改善；
	4.	如何形成可长期落地的产品修复方案。
 
⸻
 
2. 第一阶段：根据故障现象提出初始假设
根据测试方向上的明显不对称，初步提出以下假设。
2.1 假设一：物理网卡或外部链路能力不足
如果 eth0、交换链路或 PC 接收端本身只能处理 500～600 Mbps，那么 ServerVM→PC 的 UDP 和 TCP 同样应受影响。
但 ServerVM→PC 各项测试均能达到约 950 Mbps，因此物理链路的基本带宽能力正常。
该假设被排除。
2.2 假设二：Android virtio-net TX 存在固定带宽上限
Android→PC UDP 上行必须经过 virtio-net TX，因此最初怀疑 virtio TX queue、vhost 或 DSM 用户态后端只能处理约 500 Mbps。
如果该假设成立，那么 Android→ServerVM 的 UDP 发送同样会被限制，因为它们在到达 tap1 之前使用完全相同的路径。
因此，下一步需要对 Android→ServerVM 和 Android→PC 做同参数的路径 A/B 测试。
2.3 假设三：bridge 或 eth0 转发过程中大量丢包
另一个可能性是 Android 已经向 tap1 送入接近线速的数据，但在：
tap1 → br0 → eth0
中丢失了部分报文。
如果是这种情况，应看到：
	•	tap1 RX 高于 eth0 TX；
	•	tx_dropped、rx_dropped 或 qdisc drop 增长；
	•	iperf3 的 sender 高、receiver 低、丢包率高。
2.4 假设四：vhost 实现存在性能缺陷
由于启动参数使用：
virtio-net,tap=tap1,vhost
还需要判断问题是否由 vhost-net 特有路径引起。因此安排了关闭 vhost 的对照测试。
2.5 假设五：小报文 UDP 对 CPU 亲和性和队列回收更敏感
Android 的 ethtool -k eth0 显示：
tx-checksumming: off
scatter-gather: off
tcp-segmentation-offload: off
generic-segmentation-offload: off
tx-udp-segmentation: off [fixed]
DSM 代码提供的 virtio-net feature 也没有包括完整的 TX checksum、TSO、USO 等能力。并且代码只配置一个 TX queue：
#define VIRTIO_NET_RXQ  0
#define VIRTIO_NET_TXQ  1
#define VIRTIO_NET_MAXQ 3

static struct virtio_ops virtio_net_ops = {
        "vtnet",
        VIRTIO_NET_MAXQ - 1,   /* 实际只有 RXQ 和 TXQ */
        ...
};
这意味着 1400 字节 UDP 上行是一条单 TX queue、高 PPS、基本无发送卸载的路径。
按照应用层载荷计算：
1000 Mbps / (1400 × 8)
≈ 89,300 个 UDP datagram/s
因此，任何每报文固定开销都会被显著放大。
 
⸻
 
3. 第二阶段：通过路径 A/B 测试确定问题边界
3.1 Android→ServerVM 与 Android→PC 对照
使用相同 Android CPU、相同 UDP 长度和发送方式，分别把 ServerVM 和外部 PC 作为目标。
代表性结果如下：
Android CPU2 → ServerVM：1260 Mbps
Android CPU2 → PC：       472 Mbps

Android CPU3 → ServerVM：3510 Mbps
Android CPU3 → PC：       814 Mbps
selected_windows.txt
还出现过：
Android CPU1 → ServerVM：3520 Mbps
Android CPU1 → PC：       908 Mbps
同一 CPU1 另一轮到 PC：  553 Mbps
这组测试得到第一个关键结论：
Android 的 virtio-net frontend、virtqueue TX、vhost/DSM 和 TAP 公共路径不存在固定的 500～600 Mbps 上限。
如果 virtio TX 本身只能处理 500 Mbps，则 Android→ServerVM 不可能达到 1.26～3.51 Gbps。
因此，问题边界被缩小到 tap1 之后、且只有转发到物理 eth0 时才出现的路径：
tap1
  → br0 转发
  → eth0 TX
  → 物理网卡完成处理
日志关联分析使用了流量窗口、线程分类和线程 CPU 迁移三类数据。
 summary.txt
 
⸻
 
3.2 tap1 与 eth0 计数对照
在 Android→PC 测试期间，ServerVM 的统计表现为：
tap1 RX 速率 ≈ eth0 TX 速率
tap1 RX packets ≈ eth0 TX packets
tap1 rx_dropped 不增长
eth0 tx_dropped 不增长
低速测试中，iperf3 也通常表现为：
sender ≈ receiver
loss ≈ 0
这否定了“Android 已经送入 900 Mbps、bridge 或 eth0 再丢掉一半”的假设。
实际情况更符合：
下游发送队列处理速度降低后，反压逐级传回 TAP、virtio 后端和 Android 发送队列，最终导致 Android 发送端本身只能产生较低速率。
也就是说，低带宽是受限发送，而不是大量丢包。
 
⸻
 
4. 第三阶段：检查 vhost 是否为根因
4.1 vhost 开启时的代码路径
根据 DSM 中提供的代码，vhost 模式下，在 Guest 设置 DRIVER_OK 后执行：
static void virtio_net_set_status(void *vdev, uint64_t status)
{
        struct virtio_net *net = vdev;

        if (!net->vhost_net)
                return;

        if (!net->vhost_net->vhost_started &&
            (status & VIRTIO_CONFIG_S_DRIVER_OK)) {
                if (net->mevp)
                        mevent_disable(net->mevp);

                rc = vhost_net_start(net->vhost_net);
                ...
        }
}
随后：
static int vhost_net_start(struct vhost_net *vhost_net)
{
        rc = vhost_dev_start(&vhost_net->vdev);
        ...

        rc = vhost_net_set_backend(&vhost_net->vdev,
                                   vhost_net->tapfd);
        ...
}
此时主要 TX 数据面转入内核 vhost-* 线程：
Android virtqueue
    → vhost-* 内核线程
    → TAP
DSM 主线程并不是实际网络 TX 生产者。
这也解释了为什么执行：
taskset -pc 0 <DSM主进程PID>
没有改善。它只约束 DSM 主线程，不会自动改变已经独立创建的 vhost-* 内核线程。
 
⸻
 
4.2 最初关闭 vhost 后为什么仍未改善
关闭 vhost 后，数据面并没有绕过 TAP、bridge 和 eth0，只是把生产者从 vhost 内核线程替换成 DSM 用户态 TX 线程。
代码路径为：
static void virtio_net_ping_txq(void *vdev,
                                struct virtio_vq_info *vq)
{
        ...
        pthread_cond_signal(&net->tx_cond);
}
TX 线程被唤醒后：
static void *virtio_net_tx_thread(void *param)
{
        ...
        do {
                virtio_net_proctx(net, vq);
        } while (vq_has_descs(vq));
        ...
}
处理一个 descriptor chain：
static void virtio_net_proctx(struct virtio_net *net,
                              struct virtio_vq_info *vq)
{
        n = vq_getchain(...);
        ...
        net->virtio_net_tx(net, tiov, n, plen);
        vq_relchain(...);
}
在 TAP 后端中：
static void virtio_net_tap_tx(...)
{
        ...
        writev(net->tapfd, iov, iovcnt);
}
因此无 vhost 的完整路径是：
Android virtqueue
    → DSM vtnet-0:0 tx线程
    → vq_getchain()
    → writev(tapfd)
    → tap1
    → br0
    → eth0
但 DSM 创建该线程时没有设置 CPU affinity：
pthread_create(&net->tx_tid,
               NULL,
               virtio_net_tx_thread,
               net);
所以最初关闭 vhost 后，vtnet-0:0 tx 仍可在 CPU0～CPU5 之间迁移。原有的亲和性问题并没有消失，只是后端生产者换了一个线程。
这就是“去掉 vhost 仍没有好转”的直接原因。
 
⸻
 
5. 第四阶段：通过亲和性矩阵验证真正原因
5.1 vhost 模式的受控测试
首先固定实际 vhost-* 线程，再修改 eth0 唯一可见 IRQ 134 的 affinity。
测试结果如下：
vhost CPU0 + IRQ CPU0：
约 836～843 Mbps

vhost CPU0 + IRQ CPU1：
约 535～546 Mbps

vhost CPU5 + IRQ CPU5：
约 830 Mbps
由此可以排除“CPU0 性能特殊”的解释。
真正影响性能的是相对位置：
vhost 与 IRQ 同核 → 高
vhost 与 IRQ 跨核 → 低
 
⸻
 
5.2 无 vhost 模式的受控测试
无 vhost 模式下，直接绑定实际的：
vtnet-0:0 tx
并控制 IRQ 134 的 CPU。
最严格的一组对照为：
DSM TX CPU1 + IRQ CPU0：
约 625 Mbps

DSM TX CPU1 + IRQ CPU1：
约 953 Mbps
两组命令、UDP 长度和目标均相同，只改变 IRQ 所在 CPU。
同核后提升约：
(953 - 625) / 625 ≈ 52.5%
而且：
	•	跨核组稳定在约 610～633 Mbps；
	•	同核组绝大多数秒稳定在约 948～955 Mbps。
这组实验形成了强因果证据：
问题不是 vhost 本身，而是实际报文生产线程与 eth0 中断/完成处理上下文的 CPU 亲和性。
 
⸻
 
6. 根因机制分析
6.1 生产者与完成者模型
Android→PC UDP 上行串联了两套队列生命周期。
第一套是 virtio TX：
Android 提交 virtqueue descriptor
    ↓
vhost 或 DSM TX线程处理
    ↓
返回 used descriptor
第二套是物理 eth0 TX：
后端线程向 TAP 注入报文
    ↓
bridge 转发
    ↓
eth0 驱动提交 TX descriptor
    ↓
硬件发送
    ↓
IRQ 134 触发驱动后续处理
    ↓
回收 TX descriptor 和 SKB
从现有信息只能确认 IRQ 134 是 eth0 唯一可见硬中断。IRQ 之后具体由哪个 ISR、NAPI poll 或驱动函数完成 TX 回收，需要结合 eth0 驱动源码或 tracepoint 才能完全确认。
不过，亲和性矩阵已经证明：IRQ 134 的执行 CPU 与 TX 后端线程的执行 CPU之间存在直接性能关系。
 
⸻
 
6.2 同核时
例如：
DSM TX线程：CPU1
eth0 IRQ： CPU1
报文生产和物理网卡完成处理集中在同一 CPU：
CPU1：
  处理virtqueue
  → writev(tap1)
  → bridge转发
  → 提交eth0 TX
  → 处理IRQ/NAPI
  → 回收TX descriptor
这有利于：
	•	保持 TX ring 和 netdev queue 热点状态的缓存局部性；
	•	减少 SKB、descriptor 和队列状态的跨核迁移；
	•	减少远程 queue wakeup；
	•	及时回收 TX descriptor；
	•	及时解除发送队列 stop；
	•	及时返回 virtio used descriptor。
 
⸻
 
6.3 跨核时
例如：
DSM TX线程：CPU1
eth0 IRQ： CPU0
执行关系变成：
CPU1：
  生产报文、提交eth0 TX

CPU0：
  处理eth0 IRQ、完成回收
最符合当前实验结果的机制包括：
	•	TX ring 和队列热点 cache line 在两个 CPU 之间迁移；
	•	SKB、descriptor 和队列状态发生更多缓存失效；
	•	queue stop/wake 需要跨 CPU 协作；
	•	TX completion 回收延迟增加；
	•	下游可用 descriptor 恢复变慢；
	•	反压逐级传回 bridge、TAP、virtio 后端和 Android。
1400 字节 UDP 在不同带宽下大致对应：
953 Mbps ≈ 85,100 datagram/s
625 Mbps ≈ 55,800 datagram/s
558 Mbps ≈ 49,800 datagram/s
这是一条高 PPS 路径。每报文增加少量跨核固定成本，累计后就会产生数百 Mbps 的吞吐差异。
严格来说，现有测试已证明亲和性因果关系，但还没有证明微观热点一定是某个具体自旋锁或 cache line。若需要进一步定位到驱动函数，可追加：
irq_handler_entry/exit
napi_poll
net_dev_queue
net_dev_xmit
netif_tx_queue stop/wake
perf c2c
等追踪。
 
⸻
 
7. 为什么只有 Android→PC 的 UDP 上行暴露问题
这是本次调查的核心。
7.1 Android→PC UDP 上行是唯一完整串联所有环节的场景
它同时包含：
Android UDP发送
+
virtio TX
+
vhost/DSM后端线程
+
TAP
+
bridge转发
+
物理eth0 TX
+
eth0 IRQ/完成回收
没有其他测试场景完整串联这条链路。
同时它还有三个放大条件：
	1.	1400 字节固定 UDP datagram；
	2.	约 85,000～89,000 datagram/s；
	3.	单 virtio TX queue、TX offload 基本关闭。
因此它对每报文固定开销和 CPU 局部性最敏感。
 
⸻
 
7.2 Android→ServerVM UDP 为什么正常
路径为：
Android
  → virtio TX
  → vhost/DSM
  → tap1
  → br0本地交付
  → ServerVM UDP socket
它在 br0 本地结束，不进入：
eth0 TX ring
IRQ 134
物理网卡 TX completion
因此不存在：
virtio后端生产线程
       ↔
eth0完成中断
这一敏感的生产—完成协作关系。
这就是为什么同一 Android CPU 到 ServerVM 可以达到 1.26～3.51 Gbps，而到 PC 可能只有 472～814 Mbps。
 selected_windows.txt
 
⸻
 
7.3 ServerVM→PC UDP 为什么正常
ServerVM 本地产生 UDP 时，路径为：
ServerVM iperf3
  → ServerVM UDP/IP
  → qdisc
  → eth0
  → IRQ 134
它不经过：
Android virtqueue
vhost/DSM后端
tap1输入
br0从tap1向eth0转发
所以路径更短，每个报文参与的队列和线程更少。
ServerVM 的本地协议栈直接把报文提交给 eth0，没有额外的 Guest virtqueue 回收和 TAP 后端反压链。即使存在一定跨核成本，也没有被前面的 virtio/TAP/bridge 开销叠加放大到限制千兆带宽的程度。
 
⸻
 
7.4 PC→Android UDP 下行为什么正常
下行路径为：
PC
  → eth0 RX
  → IRQ/NAPI
  → br0
  → tap1
  → vhost/DSM RX
  → Android
它是物理 RX 驱动路径，而不是 Guest TX 推动物理 TX 的路径。
RX 通常由中断触发 NAPI，然后在一次 poll 中批量处理多个报文。Android 侧还显示：
generic-receive-offload: on
因此下行可通过 NAPI 和 GRO 摊薄每报文成本。
最重要的是，下行没有以下闭环：
Guest后端生产eth0 TX
       ↔
物理eth0完成回收
所以不会以同样方式受 TX 后端线程和 IRQ相对位置影响。
 
⸻
 
7.5 Android→PC TCP 上行为什么正常
TCP 并没有绕过 virtio、TAP、bridge 和 eth0，因此不能简单说“TCP 路径不同”。
真正差异在发送模型。
UDP 测试中：
一个1400字节datagram
  → 一个独立发送单位
  → 独立的数据报边界
  → 独立的SKB和virtio处理
TCP 是字节流：
iperf3提交较大的连续缓冲区
  → 内核按MSS分段
  → 多个SKB可以连续排队和批量推进
  → ACK与拥塞窗口调节发送节奏
即使 Android 当前没有启用 TSO/GSO，TCP仍能获得以下优势：
	•	用户态一次调用可提交更多字节；
	•	内核可以连续处理多个 SKB；
	•	virtqueue 中可以一次积累和处理多个 descriptor；
	•	不需要用户态为每个 1400 字节独立维护 datagram pacing；
	•	TCP 流控会更自然地适应下游队列容量。
因此，TCP对“每个独立报文的固定跨核成本”远没有小报文 UDP敏感。
需要说明：目前没有直接统计 TCP 与 UDP 的 virtqueue kick 次数、每次处理 descriptor 数量和 queue stop/wake 次数。因此“TCP批处理摊薄开销”属于与现象高度一致的机制推断，而不是已经通过 tracepoint逐项证明的结论。
 
⸻
 
8. 测试工具版本是第二个独立因素
在 vhost 和 IRQ 已经同核的情况下：
系统 iperf3 3.6+：
sender ≈ 627～642 Mbps
receiver ≈ 627～642 Mbps

本地 iperf3 3.17.1+：
sender ≈ 928 Mbps
receiver ≈ 927 Mbps
在无 vhost、DSM TX 与 IRQ 同核时，iperf3 3.17.1+ 也可以稳定产生：
sender：1000 Mbps
receiver：约954 Mbps
这说明旧版工具在某些后端节奏下，本身无法产生目标流量。
但不能直接断言是 “POSIX threads” 单独带来的提升，因为当前是单流测试，而且两个二进制都带有私有 + 后缀。编译选项、Android 适配、发送循环和 pacing 实现都可能不同。
能够严格得出的结论是：
系统 iperf3 3.6+ 不适合作为当前产品的千兆 UDP 验收源；iperf3 3.17.1+ 能稳定产生目标速率。
另外，客户端与 PC server 最好使用同一版本。当前存在 sender 1000 Mbps、receiver 954 Mbps、数据报数量几乎相同且 lost 为 0 的输出，这更像两端统计口径差异，而不是实际丢包。
 
⸻
 
9. 最终结论
本次故障由两个层次叠加产生。
9.1 产品网络路径的主要原因
ServerVM 中实际 virtio-net TX 后端线程与 eth0 IRQ 134 的 CPU 亲和性不匹配。
vhost 模式下，实际后端是：
vhost-*
无 vhost 模式下，实际后端是：
vtnet-*:*\ tx
当后端线程与 IRQ 同核时，可达到约 927～954 Mbps；跨核时可能下降到约 500～650 Mbps。
9.2 测试工具的次要原因
Android 系统 iperf3 3.6+ 对当前 vhost 后端和高 PPS UDP 场景存在明显性能敏感性。
换用 iperf3 3.17.1+ 后，在正确 affinity 配置下，vhost 和无 vhost 均能达到接近千兆线速。
9.3 已基本排除
本次问题不是：
	•	物理网卡只有 500 Mbps；
	•	bridge 中途大量丢包；
	•	virtio-net 固定吞吐上限；
	•	CPU0 是唯一高性能核心；
	•	vhost 开启本身必然性能差；
	•	关闭 vhost 即可自动解决问题。
 
⸻
 
10. 建议的解决方案
10.1 配置专用网络后端 CPU
增加可配置项：
net_backend_cpu=<cpu>
例如选择 ServerVM CPU0。
vhost 模式：
vhost-*       → ServerVM CPU0
eth0 IRQ 134  → ServerVM CPU0
无 vhost 模式：
vtnet-*:*\ tx → ServerVM CPU0
eth0 IRQ 134  → ServerVM CPU0
关键是绑定实际 TX 后端 TID，不能只绑定 DSM 主进程。
 
⸻
 
10.2 无 vhost 模式在代码中直接设置线程 affinity
建议在创建 TX 线程时直接设置，而不是启动后由脚本查找。
较完整的方式是在线程创建前设置 pthread_attr_t：
pthread_attr_t tx_attr;
cpu_set_t cpuset;
int rc;

CPU_ZERO(&cpuset);
CPU_SET(net_backend_cpu, &cpuset);

pthread_attr_init(&tx_attr);

rc = pthread_attr_setaffinity_np(&tx_attr,
                                 sizeof(cpuset),
                                 &cpuset);
if (rc != 0) {
        pr_err("virtio-net: set TX affinity failed: %d\n", rc);
}

rc = pthread_create(&net->tx_tid,
                    &tx_attr,
                    virtio_net_tx_thread,
                    net);

pthread_attr_destroy(&tx_attr);
这样可以避免线程先在其他 CPU 上运行，再被后续脚本迁移。
 
⸻
 
10.3 vhost 模式自动绑定 vhost worker
vhost TID 每次启动可能变化，因此不能写死。
应在：
vhost_net_start()成功
之后，由管理服务识别对应 vhost-* 线程，并调用：
sched_setaffinity()
或者把对应线程加入专用 cpuset。
 
⸻
 
10.4 固定 eth0 IRQ，并防止 irqbalance 覆盖
设置：
echo 0 > /proc/irq/134/smp_affinity_list
并检查：
cat /proc/irq/134/smp_affinity_list
cat /proc/irq/134/effective_affinity_list
应停止 irqbalance，或者仅排除 IRQ 134：
systemctl stop irqbalance
 
⸻
 
10.5 在生命周期变化后重新应用
以下事件可能导致 TID 或 IRQ 状态变化：
	•	ServerVM 启动；
	•	DSM 启动或重启；
	•	Android Guest 重启；
	•	vhost worker 重新创建；
	•	STR suspend/resume；
	•	eth0 驱动重新初始化；
	•	link down/up。
因此 affinity 配置必须在这些生命周期之后自动重新校验并应用。
 
⸻
 
10.6 统一测试工具
Android 与 PC 统一使用 iperf3 3.17.1+。
正式测试命令：
./iperf3 \
    -A 1 \
    --cport 41001 \
    -p 5201 \
    -c 192.168.1.1 \
    -u -4 \
    -b 1000M \
    -l 1400 \
    -t 600 \
    -i 60 \
    --udp-counters-64bit \
    --get-server-output
不使用大于 MTU 的 -l 5000 或 -l 8000 作为正式验收，因为会产生 IP 分片。
-b 0 仅用于测试路径最大能力，不用于正式验收，因为它会超发并造成丢包。

10.7 后续增强项
当前通过 affinity 已可以恢复线速，因此下列项目属于增强而不是当前故障的必要修复：
	•	virtio-net multiqueue；
	•	multiqueue TAP/vhost；
	•	VIRTIO_NET_F_MQ；
	•	checksum offload；
	•	scatter-gather；
	•	GSO/TSO/USO；
	•	增加一次唤醒处理的 descriptor 数量；
	•	减少 per-packet notify；
	•	优化 TX completion batching。
这些改进可以降低系统对单 CPU局部性的敏感度，提高多流和双向场景的扩展能力。
 
⸻
 
11. 建议的验收闭环
修复后至少完成以下验证：
	1.	Android→PC UDP 上行，-b 1000M -l 1400，60 秒连续三轮；
	2.	600 秒耐久测试；
	3.	vhost 开启和关闭各验证一次；
	4.	Android→ServerVM、ServerVM→PC、PC→Android 回归测试；
	5.	TCP 双向回归；
	6.	STR 前后再次验证 affinity；
	7.	DSM 重启和 Android Guest 重启后再次验证；
	8.	检查后端线程实际 CPU、IRQ effective affinity、drop/error 和长期稳定性。
建议验收目标：
Android→PC UDP receiver ≥ 900 Mbps
无持续性异常下降
后端线程不迁移
IRQ effective affinity保持正确
接口drop/error无异常增长
