一、vmm_mutex.c 单元测试设计

1. 公共测试前置建议

vmm_mutex.c 涉及 VCPU 当前上下文、等待队列、资源挂接、锁和断言。建议测试环境中按以下方式处理外部依赖：

vmm_scheduler_current_vcpu 作为桩函数，按用例返回当前 VCPU 对象。
vmm_scheduler_orphan_context 和 vmm_scheduler_irq_context 作为桩函数，按正常路径设置为允许当前接口执行的返回值。
vmm_manager_vcpu_resource_add 和 vmm_manager_vcpu_resource_remove 作为记录型桩函数，用于检查资源是否被添加或移除。
__vmm_waitqueue_sleep、__vmm_waitqueue_wakefirst、__vmm_waitqueue_wakeall 作为桩函数，按用例设置返回值。
vmm_spin_lock_irqsave、vmm_spin_unlock_irqrestore、vmm_spin_lock_irq、vmm_spin_unlock_irq 建议替换为无副作用测试实现，避免进入真实中断或锁相关汇编。
BUG_ON 路径不建议混入普通功能用例。若项目要求覆盖 BUG_ON，建议单独使用测试替身记录断言触发并终止当前测试流程。

2. __vmm_mutex_cleanup

⸻

用例名称：__vmm_mutex_cleanup.001.R

测试目的：验证当待清理 VCPU 是互斥锁拥有者且互斥锁处于加锁状态时，清理函数能够释放互斥锁并唤醒所有等待对象。
用例类别：基于需求的测试
预置条件：构造有效 VCPU、有效互斥锁对象和互斥锁资源对象；互斥锁处于加锁状态，拥有者为当前传入的 VCPU；等待队列唤醒全部接口作为记录型桩函数；锁相关接口采用无副作用测试实现。
测试步骤：step1、构造一个互斥锁对象，并通过其资源成员作为 vcpu_res 入参；step2、设置互斥锁加锁计数为非 0，设置互斥锁拥有者为传入的 VCPU；step3、调用 __vmm_mutex_cleanup；step4、观察互斥锁状态、拥有者状态以及唤醒全部等待对象桩函数调用情况。
用例来源：需求分析、有效等价类
追溯ID：__vmm_mutex_cleanup
等价列表：VCPU 有效，VCPU 资源有效，互斥锁已加锁且拥有者为该 VCPU。
其它说明：本用例覆盖清理函数释放锁并唤醒所有等待者的正常路径。
通过准则：互斥锁加锁计数被清零，互斥锁拥有者被置空，唤醒全部等待对象接口被调用一次，函数正常返回。

二、vmm_notifier.c 单元测试设计

1. 公共测试前置建议

vmm_notifier.c 的核心是维护 notifier 链表，并按优先级顺序调用回调函数。建议在 User Code 中准备若干个测试回调函数，用于记录调用顺序、调用次数、传入的 val 和 void *v 参数，并按用例返回 NOTIFY_DONE、普通通知返回值或带 NOTIFY_STOP_MASK 的返回值。

测试 atomic notifier 时，vmm_spin_lock_irqsave 和 vmm_spin_unlock_irqrestore 建议使用无副作用测试实现。
测试 blocking notifier 时，vmm_semaphore_down 和 vmm_semaphore_up 建议使用无副作用记录型桩函数。
raw notifier 不涉及锁或信号量，主要验证链表注册、注销和调用顺序。
本文件没有对 nc == NULL 或 n == NULL 做防御，不建议构造空链表控制对象或空 notifier block 作为无效输入用例，否则会产生空指针访问，不属于当前实现的可控错误分支。

15. vmm_notifier.c static 核心函数覆盖说明

notifier_chain_register、notifier_chain_cond_register、notifier_chain_unregister、notifier_call_chain 为 static 核心函数。普通情况下不需要单独建立独立用例，因为它们已经分别通过 atomic、blocking 和 raw notifier 的公开接口间接覆盖。

若项目要求 static 函数直接建用例，可按以下方式映射：

notifier_chain_register 的空链表注册、优先级插入和同优先级追加行为，可由 vmm_raw_notifier_register.001.R、vmm_raw_notifier_register.002.R 补充直接用例。
notifier_chain_cond_register 的新节点插入和重复注册忽略行为，可由 vmm_blocking_notifier_cond_register.001.R、vmm_blocking_notifier_cond_register.002.R 补充直接用例。
notifier_chain_unregister 的注销成功和未找到路径，可由 raw 或 atomic 注销用例补充直接用例。
notifier_call_chain 的全量调用、调用数量限制、停止标志、空链表路径，可由 __vmm_raw_notifier_call 或 __vmm_atomic_notifier_call 用例补充直接用例。

三、两个文件的额外风险说明

vmm_mutex.c

不建议将 mut == NULL 的普通用例作为返回值用例，因为接口使用 BUG_ON 处理空指针，不是错误码返回。
vmm_mutex_lock 和 vmm_mutex_lock_timeout 中如果等待队列睡眠桩函数返回 VMM_OK，但没有模拟锁释放，while (mut->lock) 可能持续循环。因此等待成功路径必须让等待桩函数在合适时机模拟锁变为可用，或者通过其它方式避免无限循环。
vmm_mutex_trylock 对 orphan 上下文有断言式前置条件，非法上下文用例应作为断言路径用例，而不是普通返回值用例。

vmm_notifier.c

不建议构造 nc == NULL 或 n == NULL 用例，因为当前实现没有空指针防御。
notifier 注册会按优先级降序排列，新节点优先级大于当前节点时插入到当前节点之前；优先级相等时会排在已有同优先级节点之后。若详设明确要求同优先级稳定插入，可增加一个同优先级注册用例。
nr_to_call 为负数时表示实际不限制调用数量，因为循环条件中负数为真，遍历会直到链表结束；普通简化接口正是使用该行为。
